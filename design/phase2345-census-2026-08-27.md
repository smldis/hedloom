# Phases 2–5 census: pruner, pins, and retention trigger

**Measured 2026-08-27 against `0bc8040`, after Phase 1 landed.** This is a
code census, not a description of implemented behaviour. No Phase 2–5 source
or test change was made during the census.

## Verdict

The plan is implementable without changing its architecture. Phase 1 landed
the record/try split, layout declaration, per-try manifests, standing pointer,
pure workspace resolver, try names, alias scan, and claim-aware publication
that Phases 2–5 require. The two pre-existing claim/publication defects named
by the plan are already fixed on `main`: `accept_for_reuse()` holds
`journal.claim()` and diagnostics writes are guarded so an unwritable
workspace cannot erase terminal publication.

The required baseline matches exactly:

```
tests       58 passed, 2 skipped
exec/tests 274 passed
run/tests   73 passed, 2 skipped
flow/tests  93 passed
combined   498 passed, 4 skipped
```

Three signature sketches need implementation detail that the plan does not
show, but none changes the settled surface:

1. `RetentionRule` has no `plan` or `invocation` field although the CLI offers
   those filters. They remain CLI prefilters over records; the public rule
   signature stays as written.
2. `Pin`/`FrozenFile` deliberately expose the frozen inventory, but the sketch
   omits original filesystem modes even though `unpin(thaw=True)` must restore
   them. The `pinned` event must carry a private `modes` mapping in addition to
   the public pin document. This is durable implementation evidence, not a new
   public field or promise.
3. `[retention.automatic]` is outside `RetentionPolicy`'s Phase 2 signature.
   `Site` therefore retains the full raw retention mapping; the policy parses
   `floor` and `rule`, while the post-run trigger reads and validates
   `automatic.after_run` separately and selects those named rules.

## Phase 3: destructive apply

`AttemptJournal.claim()` is non-blocking and raises `ConcurrentClaim`, which
maps directly to the planned `contended` skip. `append()` currently recognises
no `workspace_removed` event, and `fold()` has no removed-workspace field.
Phase 3 must add the event vocabulary while leaving try allocation derived
from `try_started` events, so pruning cannot reuse a try number.

`Survey.apply()` must reconstruct every precondition under the record claim;
the survey is only a proposal. The removal event precedes filesystem mutation.
If a prior pass wrote the event and crashed before removal, a later apply may
finish the same removal: the event is evidence of intent and the still-present
workspace is the unfinished side effect. Record directories, manifests,
standing evidence, and aliases are never removed.

There is no existing workspace deletion path in `exec`, `run`, or the façade.
The new code is therefore the only destructive path and can keep all deletion
discipline local to `hedloom_exec.prune`.

## Phase 4: pins

`AttemptState` has no `pins` field, as explicitly deferred from Phase 1 by the
brief. Phase 4 must add it and fold `pinned`/`unpinned` events without changing
the per-try execution projection. The journal requires every event to carry a
non-negative `try`, which already matches the settled per-try-only pin model.

Pinning can derive the workspace solely from `(workspace_root,
try_name(identity, try_number))`; no Plan document is needed. Human selectors
can resolve from `scan_attempts()` because `AttemptRecord` already carries
`plan_id`, `authored_key`, identity, and current try. A bare record selector is
CLI sugar expanding to its terminal tries; stored pins always name one try.

The stable inventory must hash regular-file content, include symlink identity
without following targets outside the workspace, and preserve enough private
mode evidence to thaw what pinning changed. The pin itself stays in the record,
never the workspace. `chmod a-w` is a guardrail only; verification re-walks
content and reports drift, missing workspace, or layout change.

The runner already allocates a fresh workspace for every later try, so a pin
does not require in-place execution changes. `begin_try()` never reallocates a
terminal try. The explicit refusal hook is needed in any operation that would
mutate an existing pinned workspace: pruner apply and future maintenance paths;
no current runner path writes a terminal try workspace again.

## Phase 5: Site policy and post-run trigger

`Site` is a frozen dataclass. It currently owns `root`, optional independent
`workspace_root`, placement/address data, and kernel settings. `from_file()`
parses `[study]`, `[address_space]`, `[placement]`, and `[kernel]`; adding a raw
`retention` mapping is additive. The field must be copied through
`with_transports()`, `overridden()`, and `served_in_process()` or a run-mode
change would silently discard operator policy.

The common completion seam is `Study._run()`: both sequential and graph runs,
direct `Study.submit()`, and `Session.submit()` pass through it. The bounded
automatic pass belongs after the run report is complete and watcher teardown
has begun. It applies only rule names listed by the site, retains every global
safety check (`floor`, `keep_latest`, reusable, aliased, pinned,
`unreconciled`), and warns without changing the run result if pruning fails.

`Study.submit`, façade `submit`, `Session.submit`, and `session` currently have
no pruning argument. They stay that way; the Phase 5 tripwire can assert their
signatures rather than introducing study authority over retention.

## Operator surface and maintained contracts

`src/hedloom/cli.py` currently implements only `where`, `check`, and `log`,
with mutually exclusive `--site`/`--root`. `prune` and pins need both record
and workspace roots, so `--site` is sufficient and explicit root mode must
require both `--root` and `--workspace-root`. Existing query commands remain
one-root operations.

The changes add current contracts in `exec/ONTOLOME.md`, `ONTOLOME.md`, the
exec and façade guides, and site documentation. They also realize the outer
register's open workspace-garbage-collection concept, so
`../docs/vision/open-concepts.md` needs its own branch and PR in the outer
repository, cross-referenced from the Hedloom PR.

## Constraint checks

- `hedloom_exec` needs only the standard library and imports neither Hedloom
  Flow nor Dask.
- Identity, input digests, standing selection, Plan documents, and artifact
  publication do not change.
- Survey is read-only and creates no root or workspace it inspects.
- Destruction occurs only after a fresh check under the existing record claim.
- Pins are terminal-only, per-try, durable in the record, and detect rather
  than claim to prevent drift.
- Automatic retention remains site-owned; no study or body decides what is
  kept.
